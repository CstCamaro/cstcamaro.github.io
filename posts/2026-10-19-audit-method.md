## 从问题开始

打开一个陌生代码库时，我更愿意先问三个问题：谁可以提供输入？输入会经过哪些转换？最终由谁做出信任决定？

把这三个问题放在一起，代码审计就有了一条可以反复验证的阅读路径。

## 画出最小数据流

先确定外部输入和敏感操作之间最短的联系。此时的目标是理解系统，不是立即判断漏洞。

```text
HTTP request
    ↓
Route → Authentication → Authorization
    ↓
Service → Data transformation → Storage
```

建议在笔记中固定保留这些信息：

- 入口：路由、消息队列、文件导入或定时任务。
- 身份：当前主体来自哪里，是否允许匿名访问。
- 权限：检查发生在哪一层，是否与具体资源关联。
- 数据：参数经过了哪些解析、规范化或类型转换。
- 结果：最终读写了什么，是否越过预期的信任边界。

## 记录可验证的证据

一条有效的审计记录，应该能让之后的自己重新走完推理过程。相比单独记录结论，记录文件、函数、条件与观察结果更有价值。

```javascript
// 示例：将资源访问的主体和对象放在同一个检查中。
function canReadDocument(user, document) {
  return document.ownerId === user.id;
}
```

### 区分事实和假设

**事实**是从代码或实验直接得到的观察；**假设**是尚需进一步验证的解释。把它们分开写，可以减少重复工作。

| 记录项 | 示例 |
| --- | --- |
| 观察 | 资源查询接受外部传入的文档 ID |
| 假设 | 资源与主体之间可能缺少关联检查 |
| 验证 | 在授权的本地环境中添加测试用例 |

## 留下一份可复用的检查清单

1. 确认测试范围与环境。
2. 找到输入进入系统的具体位置。
3. 跟踪身份与资源权限检查。
4. 记录能够推翻当前假设的证据。
5. 写清修复思路和回归检查点。
